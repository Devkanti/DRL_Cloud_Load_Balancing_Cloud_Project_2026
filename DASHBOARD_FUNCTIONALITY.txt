1. EXECUTIVE SUMMARY & PURPOSE
================================================================================
The FlashBalanceAI Demo Dashboard is an interactive, high-resolution web 
application engineered using Dash, Plotly, and Flask. It was designed to provide 
real-time visibility into autonomous cloud load balancing under extreme burst 
conditions (such as high-concurrency e-commerce flash sales).

Key Objectives of the Dashboard:
- Visualise real-time traffic routing decisions made by a Deep Reinforcement
  Learning (DRL) agent (PPO) versus traditional heuristic dispatchers.
- Demonstrate PPO's proactive headroom-aware routing under a sudden 10x traffic
  surge (Scenario E2), proving the elimination of queue hotspots and SLA violations.
- Provide direct side-by-side comparative benchmarking across all 6 project 
  algorithms simultaneously.
- Stream live Apache JMeter 5.6.3 formatted HTTP sample logs (JTL) directly into
  an interactive browser console.

3. SIMULATION ENGINE INTERNALS (demo_runner.py)
================================================================================
The DemoJMeterRunner class executes in a dedicated background threading.Thread, 
maintaining thread-safe locks over shared telemetry structures.

A. Backend Node Model (SimulatedBackendState):
   - Pool Size: 4 backend instances (Backend #0, #1, #2, #3) simulating AWS EC2.
   - Individual Capacity: 250 requests/second each (Total Pool Capacity = 1,000 RPS).
   - Baseline Latency: Staggered base latencies (45ms, 50ms, 48ms, 52ms).
   - Non-linear Degradation Model:
     * When Active Connections <= Capacity:
       Latency(t) = Base_Latency * (1.0 + CPU_Utilisation)
     * When Active Connections > Capacity:
       Incoming requests spill over into queue_depth.
       Latency incurs exponential queue waiting delays.
     * Response Time EMA: Updated using an exponential moving average (alpha = 0.1).
     * SLA Threshold: Flagged as an SLA violation if total latency > 500 ms.

B. Scenario E2 Workload Profile (120-Second Lifecycle):
   - Seconds 0 - 20 (Baseline):
     Poisson arrival rate ~120 req/s. Well within pool capacity.
   - Seconds 20 - 30 (Ramp-Up Surge):
     Arrival rate rapidly climbs from 120 req/s to 950 req/s.
   - Seconds 30 - 90 (Peak Flash-Sale Burst):
     Arrival rate oscillates between 950 and 1,050 req/s (10x baseline burst).
   - Seconds 90 - 120 (Cool-Down & Recovery):
     Arrival rate smoothly decays back to ~200 req/s.

C. Real-Time JTL Log File Writing:
   - File Path: experiments/results/demo_live_jmeter.jtl
   - Header: timeStamp, elapsed, label, responseCode, responseMessage, 
             threadName, dataType, success, failureMessage, bytes, sentBytes
   - Outputs true JMeter 5.6.3 telemetry records every step.

3.1 HOW THE BACKEND WORKS UNDER THE HOOD (IN SIMPLE, EASY-TO-UNDERSTAND TERMS)
--------------------------------------------------------------------------------
Think of the dashboard backend as an automated air traffic controller for web 
requests. Here is what happens behind the scenes step by step:

1. THE BACKGROUND CLOCK & WORKER THREAD:
   - When the dashboard starts, it launches an independent worker thread 
     (`threading.Thread`) running `demo_runner.py`.
   - This thread acts like an invisible clock ticking once every second (or 0.5s 
     in 2x Fast-Forward mode), advancing the simulation from second 0 to 120.
   - Because it runs on a separate background thread, the web page remains fast, 
     responsive, and never freezes up.

2. TRAFFIC GENERATION (THE RUSH HOUR):
   - At every simulated second, the engine checks what phase of the flash sale it 
     is in.
   - In the beginning (0-20s), it generates light baseline traffic (~120 shoppers 
     per second).
   - When the flash sale starts (30-90s), it unleashes a 10x traffic spike (~1,000 
     shoppers per second).
   - If the operator clicks "⚡ Inject 10x Spike", it immediately injects an 
     extra surge of 1,200 requests.

3. DISPATCHING & QUEUING (THE SIX BRAINS IN PARALLEL):
   - For every single second, the engine evaluates all 6 load balancing algorithms 
     at the exact same time:
     * PPO evaluates remaining "headroom" on each server (Capacity - Active Connections). 
       It acts like a smart GPS that sees traffic building up ahead and routes cars 
       to empty lanes *before* a traffic jam happens.
     * Round-Robin blindly sends requests in a circle (Server 0, then 1, then 2, 
       then 3, repeat). When Server 1 gets slowed down by heavy computation, Round-Robin 
       keeps dumping requests on it anyway, causing a catastrophic queue pile-up.
     * DQN, Least Connections, Weighted Round-Robin, and the Autoscaler each use 
       their respective strategies in parallel.

4. SERVER PHYSICS & NON-LINEAR LATENCY:
   - Each backend has a physical capacity of 250 requests per second.
   - If a server receives fewer than 250 requests:
     * CPU utilisation stays low (< 100%).
     * The response time is super fast (~45-60 milliseconds).
   - If a server receives more requests than 250 (as happens under Round-Robin):
     * The excess requests cannot be served immediately and wait in a line (the Queue).
     * Every waiting request adds delay. The queue length quickly explodes.
     * Response time balloons to 700+ milliseconds!
     * Any request taking longer than 500 milliseconds is officially recorded as an 
       "SLA Violation".

5. THREAD-SAFE MEMORY BRIDGE (THE TELEMETRY BUFFER):
   - While the background engine is busy calculating queues and latencies, the Dash 
     web server needs to read this data without crashing or causing race conditions.
   - The engine uses a mutex lock (`threading.Lock`). When Dash asks for an update, 
     the engine safely takes a quick snapshot of:
     * Current second & phase
     * CPU utilisation of each server
     * Queue depths & active connections
     * P95 latency and SLA violations
     * Last 20 lines of the JMeter log
   - This snapshot is instantly returned as a clean Python dictionary.

6. LOG EMISSION:
   - Simultaneously, every simulated second writes formatted CSV lines into 
     `experiments/results/demo_live_jmeter.jtl`.
   - This ensures that if you open JMeter or any log viewer outside the dashboard, 
     the logs match the exact live numbers seen on your screen.

4.1 Header & Hero KPI Cards
--------------------------------------------------------------------------------
At the very top of the dashboard, four large real-time KPI indicator cards 
display live aggregate performance:
1. LIVE THROUGHPUT (req/s):
   Displays current requests processed per second with a dynamic delta badge.
2. P95 LATENCY (ms):
   Displays the 95th percentile response time. Displays in glowing Emerald Green 
   when safely below the 500 ms SLA target, and shifts to Crimson if exceeded.
3. SLA COMPLIANCE RATE (%):
   Calculated as (1 - SLA_Violations / Total_Requests) * 100%. Displays 100.0% 
   under PPO routing.
4. DRL LATENCY ADVANTAGE (%):
   Live performance edge metric computing the percentage reduction in tail 
   latency achieved by PPO compared to static Round-Robin:
   Advantage = ((RR_P95 - PPO_P95) / RR_P95) * 100% (typically 80% to 86%).

  refreshes the browser UI (options: 1s, 2s, 5s, 10s, 30s).

5. MULTI-ALGORITHM DECISION LOGIC
================================================================================
Each of the 6 algorithms implements its distinct dispatching philosophy:

1. PPO (Proximal Policy Optimization — DRL Actor-Critic):
   - Computes dynamic headroom: Headroom_i = max(0, Capacity_i - Active_Conns_i)
   - Dispatches traffic proportionally to headroom while heavily penalizing queue depth.
   - Prevents hotspots before latency spikes materialize.

2. DQN (Deep Q-Network — Value-Based DRL):
   - Estimates Q-values for each node action.
   - Achieves lower latency than static baselines, but suffers from occasional 
     oscillatory routing under sudden burst transitions.

3. Round-Robin (Static Baseline):
   - Dispatches strictly cyclically: node = (step_count) % 4.
   - Completely blind to server load, queue depth, or response times.

4. Weighted Round-Robin (Static Heuristic):
   - Dispatches according to fixed static node weights (e.g., 3:2:3:2).
   - Ineffective when traffic surges uniformly across all backend instances.

5. Least Connections (Dynamic Heuristic):
   - Dispatches to whichever node currently has the lowest active_connections count.
   - Responsive, but fails to account for queue buildup and non-linear CPU degradation.

6. Threshold Autoscaler (Rule-Based Autoscaler):
   - Routes evenly until node CPU > 75%, then attempts to shed load.
   - Suffers from autoscaling lag and hysteresis during acute 10x traffic bursts.

6. REAL-TIME TELEMETRY PIPELINE & CALLBACK FLOW
================================================================================
The dashboard uses Dash's reactive callback architecture:

1. Interval Trigger:
   A `dcc.Interval` component (ID: `interval-refresh`) fires periodically (default: 
   30,000 ms, user-configurable down to 1,000 ms).

2. Global Engine Access:
   Callbacks query `DEMO_ENGINE.get_latest_telemetry()` and 
   `DEMO_ENGINE.get_history_dataframe()` from `src/metrics/demo_runner.py`.

3. Partial DOM Patching:
   - Output 1: Hero KPI Cards (values, colors, delta badges).
   - Output 2: Active Tab Container (renders only the selected tab view).
   - Output 3: Control bar state (play/pause label, progress percentage).

4. Thread Safety:
   The background engine uses `threading.Lock()` to ensure that telemetry read 
   operations never collide with simulation state advancement.
